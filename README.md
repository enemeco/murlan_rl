# Murlan — learning table

A four-player Murlan game, a reproducible reinforcement-learning pipeline, and a web table where one person plays against three bots. Human moves are saved as they happen. Completed hands feed a background candidate learner; the serving bots change only after a candidate passes a paired evaluation.

## Play locally

Requires Python 3.10+; Python 3.11 or 3.12 is recommended.

```bash
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell instead:
# .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Open **http://localhost:8000**. Click or tap the cards themselves to select them; click again to deselect. **Luaj letrat** is enabled only when those exact cards form a legal move on your turn. There is no suggested-combination menu. **Pas** passes until the table clears; **Jep letrën** confirms a card exchange. The interface uses Albanian wording with **robotët** throughout. Three distinct Albanian names are assigned per match, remain stable across hands and reloads, and change for the next match. Reloading resumes your current game while the server process remains alive.

The app seeds `data/champion.pt` from `checkpoints/improved_policy.pt` on its first start. If the improved checkpoint is absent, it uses the original `checkpoints/murlan_policy.pt`. Missing both checkpoints starts strategic rule-based bots, and the candidate learner can bootstrap a network from demonstrations. Original checkpoint weights are never overwritten by default.

For a CPU-only PyTorch install, run this before installing the requirements:

```bash
python -m pip install torch==2.5.1 --index-url https://download.pytorch.org/whl/cpu
```

Alternatively, Docker Compose provides a persistent data volume:

```bash
docker compose up --build
```

## What changed

- **Correct multi-player credit assignment.** Separate trajectories for each seat and hand. Rewards generated by another player's terminal move still reach every participant. GAE propagates terminal rewards backward without mixing environments or players. Complete hands avoid incorrect rollout bootstrapping.
- **Stronger baselines.** Random, greedy, and strategic agents. The strategic baseline uses an exact minimum partition of its own hand into legal combinations, preserves useful combinations and control cards, and reacts to opponents' public hand sizes. It never reads their card identities.
- **A better policy input and head.** 249 observation features include own ranks, unseen rank counts, public played cards, relative player status, and recent public action semantics. A shared action-semantic head supplements the action logits. Orthogonal initialization and a separate value output stabilize optimization. This is a feed-forward policy with public-history features, not a recurrent model or a perfect-information search agent.
- **Exploration with correct probabilities.** Legal-action-only epsilon mixing (0.08 to 0.02), temperature (1.2 to 1.0), and entropy regularization decay without eliminating exploration. PPO recomputes the same mixture distribution used during collection. Clipped values, gradient clipping, KL early stopping, and finite-value checks limit unstable updates.
- **Diverse opponents.** A bounded league of frozen policies plus rule-based opponents; 40% of hands use four current policies, and the rest train one seat against the opponent mixture. Optional strategic imitation provides a useful starting policy.
- **Persistent human feedback.** SQLite stores every accepted move immediately, even from unfinished games. Human moves are supervised examples, not fabricated on-policy PPO actions. Hand outcomes weight demonstrations; the bots' own sampled decisions supply PPO experience against the human.
- **Candidate/champion separation.** Training runs on a separate copy. Serving policies stay fixed for an entire hand. Checkpoints are written atomically, and a weights fingerprint prevents PPO data from being reused after an unrelated checkpoint replaces the same version number.
- **A usable game service.** Legal-action validation, duplicate-request protection, session locks and limits, graceful missing-checkpoint behavior, real public card displays, complete move history, learning controls, and protected checkpoint download.

## Train and continue improving

Train from scratch, with strategic imitation followed by league PPO:

```bash
python train_selfplay.py --steps 500000 --n-env 8 --rollout 2048 \
  --warmstart-hands 96 --warmstart-epochs 8 \
  --eval-every 16 --eval-deals 16 --eval-mode match \
  --seed 0 --output-dir runs/league
```

Continue the included training run (the step budget is the **total** target, not additional steps):

```bash
python train_selfplay.py --resume checkpoints/training_resume.pt \
  --steps 1000000 --n-env 8 --eval-every 16 --eval-deals 16 \
  --output-dir runs/continued
```

`--resume` restores weights, optimizer, update count, and PyTorch CPU RNG. It starts fresh game environments and rebuilds the opponent pool; it is not a bit-for-bit continuation of the previous simulator. `--init checkpoints/murlan_policy.pt --warmstart-hands 0` migrates the original network and starts a new optimizer. Migration pads the original 43 inputs with zero weights and initializes the new semantic head to zero, preserving the original policy's outputs at initialization.

Add the web application's human examples to offline training:

```bash
python train_selfplay.py --init checkpoints/improved_policy.pt \
  --warmstart-hands 0 --human-db data/replay.sqlite3 \
  --steps 500000 --output-dir runs/with_humans
```

Use `--device cuda` for an appropriately installed GPU PyTorch build. Collection currently steps Python environments serially; `--n-env` provides independent game streams, not subprocess workers or a fully vectorized GPU simulator.

Each output directory contains:

| File | Purpose |
| --- | --- |
| `latest.pt` | Most recent policy, optimizer and training state; may be weaker than the champion. |
| `champion.pt` | Initial policy, then replacements that pass the evaluation gate. The initial policy is explicitly marked unvalidated. |
| `metrics.jsonl` | Loss, normalized entropy, KL, clipping, explained variance, evaluation and promotion results. |

The reward is centered hand placement: **1, 1/3, −1/3, −1** for first through fourth. There is no arbitrary pass penalty or per-card reward. This targets expected hand points; full-match validation checks the resulting behavior across exchanges and score progression. It does not directly optimize a match-level win-probability objective.

## Measure gameplay

Use identical deals, all four seats, and independent test seeds. Against each opponent type, the tested policy controls one seat while three baseline agents control the others.

```bash
python evaluate.py --policy checkpoints/murlan_policy.pt --deals 64 --seed 1700000 --output runs/original_test.json
python evaluate.py --policy checkpoints/improved_policy.pt --deals 64 --seed 1700000 --output runs/improved_test.json
python evaluate.py --policy strategic --deals 64 --seed 1700000
python evaluate.py --policy checkpoints/improved_policy.pt --mode match --deals 16 --seed 1800000 --output runs/match_test.json
```

`hand` mode measures the first hand of each match. `match` mode plays complete matches, including swaps and the 21/31/41/51 score progression. Reports include mean hand points (0–3), hand win rate, and, in match mode, match win rate. Confidence intervals cluster the four rotated seats by deal. Full-match hand statistics average within each match before combining seats, so very long matches do not dominate.

Promotion defaults to **full-match** evaluation. It requires at least eight paired deals, a positive approximate 95% lower bound for the average point improvement, no opponent type dropping more than 0.1 points, and no opponent type dropping more than five percentage points in match win rate. These are conservative practical filters, not a guarantee of superiority or convergence. Do not select checkpoints using the final test seeds.

See [the benchmark report](reports/BENCHMARK.md) for the actual included checkpoint, training budget, tested opponents, and limitations. Results from one training seed are not a multi-seed research result.

## How human learning works

1. Each accepted human move is committed to `actions` immediately, with that player's observation and legal mask. No opponent hands are sent to the browser.
2. The three bots sample from the frozen policy with 3% legal uniform exploration in learning mode. Exact behavior log-probabilities and values are retained separately for each bot.
3. At hand completion, finishing rewards finalize each bot's trajectory. The hand enters a durable training queue; outcome weights are attached to the human examples.
4. The worker normally waits for four hands and 256 sampled bot decisions. Competitive-mode hands contain no on-policy bot rows and can still train a candidate through human imitation after enough hands.
5. A candidate gets a small PPO update plus a small supervised update from a random sample of human history. Every move is retained; each update samples a bounded batch rather than applying a gradient after every click. Unfinished-hand examples receive a smaller provisional weight.
6. The candidate plays paired full-match evaluations against the current champion's benchmark results. Accepted candidates are saved and used starting with the next hand; rejected candidates leave the bots unchanged. Old-policy PPO rows are retired, while human examples remain useful.

**Stërvitje** uses sampled actions with exploration. **Sfidë** selects greedy bot actions; those actions never enter PPO. The training checkbox controls collection for the next game. Turning off collection prevents both human and bot data from that game being stored. `MURLAN_ONLINE_LEARNING=0` disables automatic updates but still allows collection for offline training.

## Persistence and deployment

Run **one application worker**. Game sessions and frozen hand policies are in memory; checkpoints, every recorded move, completed-hand queues, and update reports persist on disk. Browser reloads resume live sessions, but restarting the server ends active games. Saved human moves from incomplete games remain available for imitation.

| Environment variable | Default / purpose |
| --- | --- |
| `MURLAN_MODEL_PATH` | `data/champion.pt`; mutable serving champion. |
| `MURLAN_INITIAL_MODEL_PATH` | Bundled improved checkpoint; used only if the serving path does not exist. |
| `MURLAN_REPLAY_PATH` | `data/replay.sqlite3`; persistent experience and update history. |
| `MURLAN_ONLINE_LEARNING` | `1`; set to `0` for collection-only service. |
| `MURLAN_EVAL_DEALS` | `12`; paired full-match validation deals per update. Below 8, promotion is disabled by the gate. |
| `MURLAN_TORCH_THREADS` | `1`; CPU threads for inference/training. |
| `MODEL_DOWNLOAD_KEY` | Optional header secret for `/download-model`; without a configured secret the endpoint is disabled. |

Back up the data directory. For a live SQLite database, use SQLite's backup API rather than copying only the `.sqlite3` file while WAL writes are active. When installing a new offline champion, stop the server and replace only the serving checkpoint; its fingerprint prevents stale PPO rows from being mixed with the new weights.

`compose.yaml` mounts a durable volume. `render.yaml` now selects Render Free, enables online learning and an optional 13-minute public self-ping, and disables automatic deployment. See [KEEPALIVE_SETUP.md](KEEPALIVE_SETUP.md) for setup and limitations. Self-pinging is best effort and provides no persistent storage: experience and learned weights can be lost on sleep, restart, or redeploy. Training memory usage has not been verified on Render Free. No hosting purchase or deployment is performed by this repository.

The server bounds active sessions to 128 with a two-hour idle timeout. Before opening the service broadly, put normal authentication and rate limits in your hosting layer and plan backups/retention for the growing replay database. The included application is a single-server research/game prototype, not a distributed service.

## Rules implemented

This retains the repository's rule variant: 52 cards plus black/red jokers; rank order 3 through A, 2, black joker, red joker; 54 cards dealt round-robin. Legal combinations are singles, pairs, triples, quads, and 5–12-card straights from 3 through A, plus the special low A–2–3–4–5. Equal-kind responses must have the same size and higher primary rank. Any quad beats a non-quad; quad-on-quad requires a higher rank.

The first hand must open with 3♠. In later hands the previous first-place player gives a rank 3–10 card to the last-place player and receives their highest card; if no eligible card exists, the giver's lowest card is used. The previous last-place player starts, except when holding both jokers, which skips the exchange and lets the previous winner start. A pass lasts for the trick. An exhausted last actor gives the next lead to the next active seat.

Points are 3/2/1/0. Multiple players reaching the target in the same hand raise it by 10, capped at 51. At that cap a unique score leader wins; tied leaders continue. Local Murlan variants may differ; change the engine and its tests if your house rules differ.

## Verification

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

Tests cover GAE terminal rewards, seat separation, legal exploration, checkpoint migration, finite PPO updates, complete games, hidden-card isolation, score-cap ties, API validation, request idempotency, durable human moves, collection opt-out, policy snapshots, and promotion/rejection. The interface has also been exercised in a browser for selecting/playing, passing, history, rules and reload recovery.

Algorithm background: [PPO in OpenAI Spinning Up](https://spinningup.openai.com/en/latest/algorithms/ppo.html). League opponents and demonstration learning are practical additions here; this implementation does not claim to reproduce NFSP or establish a game-theoretic equilibrium.
